Hook · activation of prior knowledge
Sound familiar?
"Has anyone ever had a query that took 45 minutes to run - and had no idea why or how to make it faster?"
query running... 12 min query running... 28 min query running... 41 min connection timeout
Traditional databases mix storage and compute together. When queries get slow, your only option is to upgrade the entire server - expensive and slow to provision.

Snowflake separates them. Scale compute up for a big query. Scale back down when done. Pay per second.
Core concept
Four things to understand
⚡

Virtual Warehouse

The compute engine that runs your queries. You can have multiple, each a different size. Start it before querying, suspend when done. You only pay while it is running.

XS / S / M / L / XL
🗄️

Database and Schema

Data is organised in three layers. Database contains schemas. Schemas contain tables and views. Same structure you know from PostgreSQL and MySQL.

database.schema.table
📝

Worksheet

The browser-based SQL editor built into Snowflake. Write queries, run them, see results - no client software needed. Share worksheets with teammates.

Snowsight UI
🔀

Separated compute and storage

This is the key idea. Storage holds your data. Compute runs your queries. They scale independently. Multiple teams can query the same data with separate warehouses.

scale up · scale down · pay per second

Raw data is loaded into Snowflake by ingestion tools. dbt transforms it inside Snowflake by running SQL models. BI tools query Snowflake to build dashboards. Snowflake is the centre of gravity - everything else connects to it.
Git connection: When you run dbt in a CI/CD pipeline, it connects to Snowflake and runs your models on merge. Your Git branch becomes a Snowflake schema. Code review protects your production data.
Check for understanding
Quick check
Pick the best answer - no pressure.
Your team runs a large monthly report that takes 20 minutes on your current warehouse size. What is the most cost-effective Snowflake approach?
A
Upgrade to a permanently larger warehouse so all queries run faster
B
Scale up the warehouse for the monthly run, then scale back down
C
Run the report across multiple smaller databases to split the load
D
Export the data to a local machine and run the query there
✓ B is correct. This is the key benefit of separating compute from storage. You scale the virtual warehouse up for the heavy monthly job, run it, then scale back to the smaller size. You only pay for the larger compute while it is actually running. Option A would mean paying for large compute 24/7 even when not needed.

The stack connection: Every tool in the modern data stack connects to Snowflake. dbt runs models inside it. Fivetran loads data into it. Looker queries it. Git version-controls the code that transforms it. Snowflake is not just a database - it is the centre of your entire data platform.
