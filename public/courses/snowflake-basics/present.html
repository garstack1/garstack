Hook · activation of prior knowledge
Sound familiar?
"Has anyone ever had a query that took 45 minutes to run - and had no idea why or how to make it faster?"
query running... 12 min query running... 28 min query running... 41 min connection timeout
Traditional databases mix storage and compute on the same server. When queries get slow, your only option is to upgrade the entire server - expensive and slow to provision.

Snowflake separates them. Scale compute up for a big query. Scale back down when done. Pay per second.
Core concept
Four things to understand
⚡

Virtual Warehouse

The compute engine that runs queries. Different sizes, pay per second. Start before querying, suspend when done.

XS / S / M / L / XL
🗄️

Database and Schema

Data organised in three layers. Database contains schemas. Schemas contain tables. Same structure you know from SQL.

database.schema.table
📝

Worksheet

The browser-based SQL editor. Write queries, run them, see results. No client software. Share with teammates.

Snowsight UI
🔀

Separated compute and storage

Storage holds data. Compute runs queries. They scale independently. Multiple teams can query the same data simultaneously.

scale up · pay per second

Raw data is loaded into Snowflake. dbt transforms it inside Snowflake. BI tools query Snowflake to build dashboards. Snowflake is the centre of gravity.
Git connection: When dbt runs in CI/CD, it connects to Snowflake on merge. Your Git branch becomes a Snowflake schema. Code review protects your production data.
Check for understanding
Quick check
Pick the best answer - no pressure.
Your team runs a large monthly report that takes 20 minutes on your current warehouse size. What is the most cost-effective Snowflake approach?
A
Upgrade to a permanently larger warehouse so all queries run faster
B
Scale up the warehouse for the monthly run, then scale back down
C
Run the report across multiple smaller databases to split the load
D
Export the data to a local machine and run the query there
✓ B is correct. Scale up for the heavy job, run it, scale back down. You only pay for the larger compute while it is running. Option A would mean paying for large compute 24/7 even when not needed - that is exactly the problem Snowflake was designed to solve.
